Architecture — as implemented

Manufacturing Analytics Pilot

ERP-shaped extracts — item master, 3–9 level BOMs, routings, work centres, weekly forecast snapshots, orders and stock — land in SQL Server, pass a classified data-quality gate, and drive a week-by-week plant simulation that carries backlog forward. Every number the API serves arrives with an evidence object: formula, named inputs with source record IDs, calculation trace, assumptions, and a MEASURED / DERIVED / ASSUMED tag.

source data evidence-bearing result gate — can stop a number

Hover or focus any box for a real example from the code or the live seed-42 run.

Scope, stated plainly: the sources are a seeded synthetic analogue of Infor M3 / MES data (seed 42), not a client extract. There is no live connection to M3, IBM i, Qlik Cloud, Bright Analytics or an MES: the adapters are simulated file adapters, and every M3 table name in docs/M3_MAPPING.md is an unverified hypothesis. Recorded stage times come from generated timestamps; they are shown beside the modelled lead times and never merged into them. The demo profile has no authentication. The secured profile adds API keys and least-privilege SQL logins, but not named-user authorization or any evidence of EU hosting. Everything below runs end-to-end in docker compose; the last full backend run (2026-09-30, with the database tests required) passed 201 tests with none skipped.

Anatomy of a number

A value on the dashboard is never just a value. This is the evidence object the API returns for the headline constraint figure in the live demand-shock run: an assumption can never pass itself off as a measurement, because every input carries its own provenance. Results added later also state their units, time scope, coverage, exclusions and data_origin (SYNTHETIC is a separate label from MEASURED/DERIVED/ASSUMED: a value computed from generated timestamps is still synthetic).

Two gates that stop a number from being invented

Bad input and missing evidence are handled structurally, not by convention. Both gates fail closed: the result is withheld or refused rather than guessed.

Data-quality blocking scope

GLOBAL_BLOCKINGENTITY_BLOCKINGKPI_BLOCKING

A blocking finding removes exactly its declared scope from the calculation. A routing with missing times withholds that item's KPI; unrelated items and work centres keep computing. Periods a KPI cannot be computed for persist as SQL NULL, not zero (db/ddl/002_nullable_blocked_period_results.sql).

blocked record → excluded at scope · never silently repaired · finding stays auditable

Copilot evidence gate

deterministic tool firstllm_used: false

The copilot never answers from the model's own knowledge. It runs deterministic tools against the same read models as the dashboard; if any returns nothing, the request ends with insufficient_evidence: true before a language model is called. With a key configured, the model only rewrites the evidence bundle into prose, and the bundle is returned with it. In the secured profile an external model additionally needs an explicit opt-in and receives a minimised payload.

empty tool result → fixed refusal → no LLM call
Two profiles, one code base

The demo is permissive on purpose because it holds only synthetic data. The secured profile is what would be used with client data. Both are described in docs/SECURITY.md, including what is tested and what still needs client infrastructure.

demo
Local synthetic data only. No API keys, open CORS, the dev database login; ports are published on 127.0.0.1 only. Never used with client data.
secured — start-up
validate_settings() stops the process for the demo password, the sa login, missing or short API keys, or no CORS origin. Secrets come from the environment; the compose override has no defaults.
secured — requests
Every route except /health needs X-API-Key. A reader key can read; only an operator key can run scenarios or use the copilot. Checked on a live instance: no key 401, reader on a mutation 403, operator 200.
secured — database
pilot_reader can select the vw_* views only; pilot_app reads sources and writes seven result tables, with no DDL. Both were verified by logging in as them.
not evidenced
EU hosting, TLS, encryption at rest, retention, the data processing agreement and named-user authorization. Those need the client's infrastructure and approvals.
What each scenario lever is allowed to change

Interventions act on the physical state, never on the outcome. This is why a buffer cannot fake a lead-time reduction, and why a capacity increase shows up with a lag.

demand_multiplier
Scales CAB-100 planning demand (the story uses +40 %). The extra demand is netted through the multi-level BOM, so load lands on subassembly work centres such as welding, not only on the finished-good route.
capacity_multiplier
Raises effective hours from the intervention week onward. It does not alter routing processing standards or any period before it. Queue time falls only as backlog actually drains.
buffer_boost_per_item
A one-time addition to opening inventory upstream of the constraint. It reduces net production requirement; it creates no processing capacity and leaves processing time untouched.
Calendar translation
A multiplier is converted into the work centre's own calendar: Welding 1 runs 1 shift × 8 h × 5 days = 40 h/week; the 12-week recovery at 1.10× is 44 scheduled h/week (+4 h, ≈ 48 min per workday). Arithmetic only — staffing and equipment feasibility need plant validation.
Persistence
scenario_runs stores parameters_json, the seed and a data_version (a content fingerprint of the source tables plus a hash of the analytics code); period_engine_results, material_requirements and cost_results keep every week's state. Reference cases are reused only when parameters, seed and data version all match, so changed inputs never serve a stale result; earlier runs stay as audit history. Custom runs are append-only.
Dependency direction

One-way. Routes shape responses; the analytics core takes DataFrames and returns dataclasses; only two modules talk to SQL Server.

frontend/src/
React + Plotly dashboard and Evidence Drawer. Obtains every visible number from the API; computes nothing itself.
app/main.py · app/api.py
FastAPI routes — pages, scenarios, Executive Story, copilot, DQ and parameter exports. Pydantic bounds on every request, security dependencies on every route; no planning logic in routes.
analytics/dashboard.py
Read models for the twelve pages; runs and caches the five reference cases once per process (warmed in the background at start-up); attaches evidence to every metric, point and row.
analytics/ — state
period_engine · constraint · leadtime · buffers · reconciliation — the weekly simulation and everything derived from its state.
analytics/ — history & decisions
stage_history · cost · policy · parameter_export · data_version — recorded times, economics, policy and the review package, all reading the same engine outputs.
analytics/ — planning
forecast · bom · mrp · netting · capacity — pure functions over DataFrames, no I/O.
dq/ · analytics/blocking.py
Twenty rules, classified findings, and the scoped blocking index the planning core consults before trusting a record.
integration/ · integrations/
The completeness checker over the data-request contract, and the simulated ERP / BI / MES file adapters. No external connection.
security.py · db/
Profile validation and API-key authorization; migration runner, restore tooling (validated identifiers, never overwrites) and login setup from environment secrets.
data_access · scenario_store
The only SQL boundary: load all source tables, write findings, persist and reuse scenario runs.
db/ddl/ · SQL Server 2022
Authoritative schema (28 tables) plus rerunnable db/migrations: result tables, six vw_* read models, database roles and the run data version. Effective-dated BOM and routing versions. Runs locally in Docker.
synthetic/ · loader/
Offline only: deterministic seeded generator with a planted-defect manifest and a last-step execution-history calibration, then an FK-ordered, ID-preserving load into SQL Server (a guarded refresh can update only the execution tables).
Not built, or waiting on the client

Listed so the diagram above is read at its true coverage.

Verified M3 mapping
Every M3 table name in docs/M3_MAPPING.md is a hypothesis until checked against the client's schema or Infor's documentation. No native M3 field is mapped.
Real connections
No live M3, IBM i, Qlik Cloud, Bright Analytics or MES link. The adapters are simulated; docs/INTEGRATION.md describes the concept, cadence and failure handling.
EU hosting & legal
TLS, encryption at rest, retention, residency and the data processing agreement are client infrastructure and approvals. Local controls are in docs/SECURITY.md.
Named-user authorization
API keys are service-level credentials. A secured browser UI needs an authenticating proxy or SSO in front.
WIP carrying cost & ROI
Engine WIP mixes items per work centre, so its carrying cost is reported unavailable. No ROI, profit or avoided-loss figure is produced.
Real plant data
Everything here is synthetic, including the recorded timestamps. At default thresholds 70 of 140 finished goods still lack the evidence for a policy recommendation.
